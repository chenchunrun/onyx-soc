## 1. 漏洞管理生命周期

漏洞管理是一个持续循环的过程，包含以下六个阶段：

```
发现 → 分类 → 评估 → 处置 → 验证 → 报告
  ↑_______________________________________________↓
```

### 1.1 各阶段说明

| 阶段 | 输入 | 输出 | 负责团队 |
|------|------|------|----------|
| 发现 | 扫描报告、威胁情报、厂商公告 | 漏洞列表 | 安全运营/漏洞扫描工具 |
| 分类 | 漏洞列表 | 分类后的漏洞池 | 安全分析师 |
| 评估 | 分类后漏洞 | CVSS评分、优先级 | 漏洞评估专家 |
| 处置 | 优先级列表 | 修复/缓解/接受风险 | 运维/安全团队 |
| 验证 | 修复记录 | 验证报告 | 安全运营 |
| 报告 | 所有阶段数据 | 管理报告、趋势分析 | 安全运营负责人 |

## 2. 漏洞发现

### 2.1 发现来源

| 来源 | 频率 | 覆盖范围 | 说明 |
|------|------|----------|------|
| 漏洞扫描器（Qualys/Rapid7/绿盟） | 每周全量，关键资产每月 | 操作系统、应用、中间件、网络设备 | 自动扫描 |
| 渗透测试 | 每半年/重大变更后 | 全范围深度测试 | 人工测试 |
| 威胁情报 | 实时 | CVE/CNVD/CISA KEV | 自动订阅推送 |
| 厂商安全公告 | 实时 | 自有系统使用的软件 | 手动订阅 |
| 安全众测/Bug Bounty | 持续 | 互联网暴露面 | 外部白帽 |
| 代码安全扫描（SAST/DAST） | 每次发布 | 自研应用 | CI/CD集成 |
| 入侵检测告警 | 实时 | 网络边界 | 安全设备 |

### 2.2 扫描策略

**全网扫描频率：**
| 资产类型 | 扫描频率 | 扫描深度 |
|----------|----------|----------|
| 互联网暴露系统 | 每周 | 深度扫描 |
| 核心业务系统 | 每月 | 标准扫描 |
| 一般内部系统 | 每季度 | 标准扫描 |
| 静态资产 | 重大变更后 | 标准扫描 |
| 自研应用 | 每次发布前 | SAST+DAST |

**扫描前准备：**
- 提前通知运维团队
- 确认扫描窗口（建议非工作时间）
- 准备应急回滚方案
- 确认扫描不影响生产系统

## 3. 漏洞分类

### 3.1 分类维度

| 维度 | 类别 | 说明 |
|------|------|------|
| 漏洞类型 | 操作系统、应用、中间件、网络设备、物联网、移动端 | 按受影响组件分类 |
| 漏洞来源 | 扫描发现、情报通知、厂商公告、人工测试 | 按发现方式分类 |
| 漏洞领域 | 内网、外网、云环境、容器、移动端 | 按暴露面分类 |
| 可利用性 | 有公开PoC/EXP、无公开利用、理论风险 | 按利用难度分类 |
| 修复难度 | 热补丁、需停机、可接受风险 | 按处置难度分类 |

### 3.2 去重与合并

- 同一CVE在不同扫描工具中的重复发现 → 合并为一条
- 同一主机上的多个相关漏洞 → 可关联分析
- 不同环境的同一软件漏洞 → 视为同一漏洞族处理

## 4. 漏洞评估

### 4.1 CVSS v3.1 评分方法

#### Base Metrics（基础度量）

**攻击向量（AV）：**
| 值 | 描述 | 评分 |
|----|------|------|
| Network (N) | 网络远程可利用 | 0.55 |
| Adjacent (A) | 需要在同一物理/逻辑网络 | 0.62 |
| Local (L) | 需要本地访问 | 0.55 |
| Physical (P) | 需要物理接触 | 0.20 |

**攻击复杂度（AC）：**
| 值 | 描述 | 评分 |
|----|------|------|
| Low (L) | 无特殊条件限制 | 0.77 |
| High (H) | 存在特殊条件（如 Timing、Resource、Social） | 0.44 |

**所需权限（PR）：**
| 值 | 描述 | 评分 |
|----|------|------|
| None (N) | 无需权限 | 0.85 |
| Low (L) | 需要低权限 | 0.62 |
| High (H) | 需要高权限 | 0.27 |

**用户交互（UI）：**
| 值 | 描述 | 评分 |
|----|------|------|
| None (N) | 无需用户交互 | 0.85 |
| Required (R) | 需要用户交互 | 0.62 |

**CIA影响：**
| 影响 | None (N) | Low (L) | High (H) |
|------|----------|---------|---------|
| Confidentiality (C) | 0.00 | 0.22 | 0.56 |
| Integrity (I) | 0.00 | 0.27 | 0.55 |
| Availability (A) | 0.00 | 0.22 | 0.56 |

### 4.2 评分计算示例

**示例1：Apache Log4j远程代码执行（CVE-2021-44228）**
```
CVSS Vector: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
- AV: Network (远程利用) = 0.55
- AC: Low (无特殊条件) = 0.77
- PR: None = 0.85
- UI: None = 0.85
- Scope: Unchanged = 不变
- C: High = 0.56
- I: High = 0.55
- A: High = 0.56

CVSS Score: 10.0 (Critical)
→ 修复优先级: P0（24小时内）
```

**示例2：Windows本地提权漏洞**
```
CVSS Vector: CVSS:3.1/AV:L/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H
- AV: Local = 0.55
- AC: High = 0.44
- PR: Low = 0.62
- UI: None = 0.85
- C: High = 0.56
- I: High = 0.55
- A: High = 0.56

CVSS Score: 7.8 (High)
→ 修复优先级: P1（7天内，核心资产）
```

### 4.3 优先级判定矩阵

| CVSS评分 | 核心资产 | 重要资产 | 一般资产 |
|----------|----------|----------|----------|
| **9.0-10.0** | P0 | P0 | P0 |
| **7.0-8.9** | P1 | P1 | P2 |
| **4.0-6.9** | P2 | P3 | P3 |
| **0.1-3.9** | P4 | P4 | P4 |
| **0.0** | Informational | Informational | Informational |

### 4.4 特殊优先级调整

**必须强制P0的情况：**
- CISA KEV目录中的漏洞（无论CVSS评分）
- 存在公开可利用的PoC/EXP
- 已被在野利用（已在野利用）
- 影响核心基础设施的漏洞

**可以降低优先级的情况：**
- 有充分补偿控制措施
- 漏洞位于隔离网络中且无可达路径
- 系统已计划退役
- 有明确的缓解计划且风险可接受

### 4.5 漏洞情报来源优先级

| 优先级 | 来源 | 用途 |
|--------|------|------|
| P0 | CISA KEV Catalog | 强制跟踪，立即处理 |
| P1 | NVD (nvd.nist.gov) | CVE详细信息、CVSS评分 |
| P1 | CNVD (cnvd.org.cn) | 国内受影响系统信息 |
| P2 | 厂商安全公告 | 官方补丁信息 |
| P2 | SecurityFocus (bid) | 漏洞详细信息 |
| P3 | Exploit-DB | PoC/EXP信息 |
| P3 | GitHub Security Advisories | 开源组件漏洞 |

## 5. 漏洞处置

### 5.1 处置方式

| 处置方式 | 适用场景 | 时限要求 |
|----------|----------|----------|
| **紧急修复** | P0漏洞，有可用补丁且可立即部署 | ≤24小时 |
| **计划修复** | P1/P2漏洞，有可用补丁 | ≤7天（P1）/≤30天（P2） |
| **缓解措施** | 暂无补丁，需临时控制风险 | 缓解措施24小时内，持续到补丁可用 |
| **接受风险** | 风险可接受且有充分补偿控制 | 需正式风险审批 |
| **弃用系统** | 系统无法修复且不再使用 | 立即下线 |

### 5.2 处置流程

```
漏洞发现 → 安全分析师评估 → 分配责任人
    ↓
    ├→ 有补丁：运维团队修复 → 安全团队验证
    │                        ↓
    │                   通过 ← 通过：关闭工单
    │                        ↓
    └─ 无补丁：安全团队制定缓解方案 → 实施缓解 → 持续监控
                                        ↓
                                   补丁发布 → 修复 → 验证
```

### 5.3 修复SLA

| 优先级 | 响应时限 | 修复时限 | 验证时限 |
|--------|----------|----------|----------|
| P0 | 1小时内 | 24小时内 | 修复后24小时内 |
| P1 | 4小时内 | 7天内 | 修复后48小时内 |
| P2 | 1个工作日内 | 30天内 | 修复后7天内 |
| P3 | 3个工作日内 | 90天内 | 修复后14天内 |
| P4 | 5个工作日内 | 180天内或接受风险 | 修复后30天内 |

### 5.4 补丁管理

**补丁测试流程：**
1. 在测试环境验证补丁兼容性
2. 验证业务功能不受影响
3. 准备回滚方案
4. 在维护窗口部署到生产环境
5. 验证业务正常和漏洞已修复

**紧急补丁部署流程（P0）：**
1. 确认漏洞和影响范围
2. 获取厂商官方补丁
3. 评估紧急部署风险
4. 如果风险低于漏洞风险 → 执行紧急部署
5. 通知相关业务方
6. 记录紧急部署决策原因

## 6. 漏洞验证

### 6.1 验证方法

| 验证方法 | 说明 | 适用场景 |
|----------|------|----------|
| 重新扫描 | 使用漏洞扫描器验证修复 | 所有漏洞修复后 |
| 手动验证 | 检查版本、配置、补丁安装状态 | 无法扫描的系统 |
| PoC验证 | 使用公开PoC验证漏洞可利用性 | 高风险漏洞处置前 |
| 渗透测试 | 深度验证修复效果 | 重大漏洞修复后 |

### 6.2 验证通过标准

- 漏洞扫描器不再报告该漏洞
- 版本号/补丁号符合预期
- 配置已按要求修改
- 相关日志无异常

## 9. 常见问题与处置原则

### 9.1 无法修复的漏洞处置

| 情况 | 处置方式 |
|------|----------|
| 供应商不提供补丁 | 联系供应商获取缓解方案；考虑替代产品 |
| 系统即将退役 | 加快退役计划；加强监控 |
| 修复影响业务 | 评估业务影响；制定分阶段修复计划 |
| 云平台底层漏洞 | 依赖云厂商修复；评估临时缓解措施 |

### 9.2 漏洞与业务冲突处置

**原则：安全不凌驾于业务之上，但也不能为业务让路。**

1. 充分评估漏洞真实风险（CVSS不是唯一标准）
2. 量化业务中断风险和漏洞被利用风险
3. 寻找平衡点：分阶段修复、灰度发布、切换窗口
4. 如果无法达成共识，升级到CISO/CIO决策
5. 所有决策必须书面记录
